# 게스트 진도 → 로그인 이관

백로그 7번 작업의 산출물입니다. **DB 변경 없음** — 1번에서 만들어 둔 `merge_guest_progress` RPC 를 사용합니다.

검증: `npm run verify:guest-merge`

---

## 1. 기존에 이미 있었습니다 — 그리고 제가 깨뜨려 놨습니다

문서가 *"AuthContext 에 이미 게스트 → 계정 처리가 일부 있는지 먼저 확인하고 중복 구현하지 마"* 라고 했고, 실제로 `mergeLocalStorageProgress` 가 있었습니다.

문제는 **1번 작업이 그걸 망가뜨렸다**는 점입니다.

```ts
// 기존 코드
const records = solvedIds.map((pid) => ({ user_id: userId, problem_id: pid }));
await supabase.from('user_solved_problems').upsert(records, { ... });
```

1번에서 넣은 트리거 두 개가 이 대량 upsert 를 거부합니다.

| 트리거 | 결과 |
|---|---|
| `solved_rate_limit` (분당 30건) | **31번째 행에서 예외 → 문장 전체 롤백** |
| `enforce_known_problem_id` | 미등록 id 하나로 **문장 전체 롤백** |

즉 **30문제 넘게 푼 게스트는 병합이 통째로 실패**했습니다. 이 기능이 존재하는 이유인 바로 그 사용자들이 대상이었습니다.

`merge_guest_progress` RPC 로 교체했습니다 — 유효 id 필터링, 속도제한 우회, 멱등성을 전부 서버에서 처리합니다.

## 2. 더 큰 버그 — 신규 가입자는 아예 병합되지 않았습니다

```ts
if (error || !data) {
  // 프로필이 없음 → 생성
  setProfile(newProf);
} else {
  setProfile(data);
  await mergeLocalStorageProgress(userId);   // ← else 안에만 있었음
}
```

**신규 회원가입은 프로필 행이 없어서 위쪽 분기로 갑니다.** 게스트로 문제를 풀다가 가입한 사람은 **진도를 전부 잃었습니다.** 조용히요.

이게 이 기능의 가장 흔한 시나리오입니다 — 게스트로 써보고 마음에 들어서 가입하는 흐름. 그 경로만 정확히 빠져 있었습니다.

이제 분기 바깥에서 호출합니다. `verify:guest-merge` 가 이 조건을 검사합니다.

## 3. 병합 규칙

| 데이터 | 방식 | 근거 |
|---|---|---|
| 해결한 문제 | `merge_guest_progress` RPC (합집합) | 속도제한 우회 + 미등록 id 필터 + 멱등 |
| 오답노트 | 클라이언트에서 미등록 id 필터 후 upsert | 속도제한은 없지만 id 검증은 동일 적용 |
| 학습가이드 챕터 | upsert | FK·속도제한 없음 |
| 퀴즈 답안 | upsert | 동일 |
| 샌드박스 실행 횟수 | **합산** | 집합이 아니라 카운터 |
| 스트릭 | **병합하지 않음** | 1번 이후 서버가 `solved_at` 에서 계산 |
| 마지막 해결일 | **병합하지 않음** | 동일 |

스트릭을 보내지 않는 게 핵심입니다. 보내도 `protect_profile_stats` 트리거가 무시하고, 어차피 방금 넣은 행들로부터 **자동 재계산**됩니다.

### 게스트 키와 사용자 키를 둘 다 읽습니다

```ts
for (const key of [`${prefix}${userId}`, `${prefix}guest`]) { ... }
```

사용자 키는 보통 서버의 사본이라 무의미해 보이지만, **오프라인에서 푼 문제**는 그것만이 유일한 기록입니다 (`syncSolvedToSupabase` 가 실패했을 때). RPC 가 멱등이라 이미 아는 id 를 다시 보내도 비용이 없습니다.

### 실패하면 게스트 키를 지우지 않습니다

```ts
if (!solvedFailed) { /* 게스트 키 삭제 */ }
```

병합이 실패하면 키가 남아 **다음 로그인에 재시도**합니다. 중복 방지 플래그도 함께 해제합니다.

### 중복 실행 방지

`fetchProfile` 은 토큰 갱신이나 탭 복귀 때마다 실행됩니다. `mergedForUserRef` 가 없으면 RPC 는 멱등이라 괜찮지만 **"23개를 저장했어요" 알림이 세션 내내 반복**됩니다. 로그아웃 시 플래그를 비워 다른 계정이 자기 게스트 데이터를 병합할 수 있게 합니다.

## 4. 사용자에게 보이는 것

### 병합 알림

로그인 직후 상단에 한 번 뜹니다. 병합된 게 없으면 **아무것도 띄우지 않습니다.**

```
이전에 푼 23개 문제를 계정에 저장했어요!
  (지금은 없는 문제 2개는 제외)
```

실패 시:

```
진도를 계정에 저장하지 못했어요. 다음 로그인에 다시 시도합니다.
```

### 로그인 유도 배너

게스트가 **3문제**를 풀면 하단에 배너가 뜹니다.

```
3개를 푸셨어요. 진도를 저장하려면 로그인하세요 —
다른 기기에서도 이어서 풀 수 있어요.           [로그인] [X]
```

- **모달이 아니라 배너입니다.** 문제 풀이를 막지 않습니다 (문서 요구사항)
- 닫으면 **그 세션 동안** 다시 안 뜹니다. `localStorage` 가 아니라 React state 라서, 나중에 다시 방문하면 한 번 더 보입니다 — 세션 안에서 조르지 않으면서 잊지도 않게
- 3문제는 "잃을 게 생긴" 시점이면서 첫 방문자를 바로 붙잡지 않는 지점입니다

## 5. 자동 검증이 잡는 것

`npm run verify:guest-merge` 는 **소스를 읽어** 아래를 확인합니다.

| 검사 | 왜 |
|---|---|
| 앱이 쓰는 게스트 키 7개가 전부 병합되거나 의도적으로 제외되는지 | **새 게스트 데이터를 추가하고 병합을 잊으면 조용히 사라집니다.** 타입 체크로는 절대 안 잡힙니다 |
| 성공 후 전부 정리되는지 | 안 지우면 매 로그인마다 재병합 |
| `streak`/`last_solved_date`/`solved_count` 를 직접 쓰지 않는지 | 001 의 보호 트리거가 무시하므로 쓰면 버그 |
| `merge_guest_progress` RPC 사용 여부 | 직접 upsert 하면 31번째 행에서 전체 중단 |
| `user_solved_problems` 직접 upsert 가 없는지 | 동일 |
| 미등록 id 필터 존재 | 하나로 전체 중단 |
| **프로필 유무와 무관하게 호출되는지** | else 안에만 있으면 신규 가입자가 진도를 잃음 |
| 중복 실행 방지 | 없으면 알림이 반복 |

현재 결과:

```
앱이 쓰는 게스트 키: 7개
  pyquests_docs_quiz_answers_guest     병합 + 정리
  pyquests_last_solved_date_guest      미병합(서버가 계산) + 정리
  pyquests_read_chapters_guest         병합 + 정리
  pyquests_review_ids_guest            병합 + 정리
  pyquests_sandbox_runs_guest          병합 + 정리
  pyquests_solved_ids_guest            병합 + 정리
  pyquests_streak_guest                미병합(서버가 계산) + 정리
```

## 6. 브라우저에서 직접 확인할 항목

문서가 요구한 세 가지입니다. **자동 검증이 대체하지 못합니다.**

### (a) 게스트로 풀고 로그인 → 진도 유지

1. 시크릿 창으로 접속 (로그아웃 상태)
2. 문제 **4개 이상** 풀기 → 3개째에 하단 배너가 떠야 함
3. 로그인
4. 상단에 **"이전에 푼 N개 문제를 계정에 저장했어요!"**
5. 대시보드의 solved 수가 N 이상인지
6. F12 → Application → Local Storage 에서 `pyquests_*_guest` 키가 **전부 사라졌는지**

### (b) 이미 진도가 있는 계정으로 로그인 → 기존 데이터 유실 없음

1. 기존 계정으로 로그인해 solved 수를 **기록**
2. 로그아웃 → 게스트로 **다른** 문제 2개 풀기
3. 같은 계정으로 다시 로그인
4. solved 수가 **기록값 + 2** 인지 (덮어쓰기가 아니라 합집합)

### (c) 병합 도중 네트워크를 끊었을 때

1. 게스트로 몇 문제 풀기
2. F12 → Network → **Offline** 체크
3. 로그인 시도 → 실패 알림
4. Local Storage 에 `pyquests_solved_ids_guest` 가 **남아 있는지**
5. Offline 해제 후 다시 로그인 → 이번엔 병합되는지

### (d) 30문제 초과 — 이번 수정의 핵심

게스트로 **31개 이상** 풀고 로그인했을 때 전부 저장되는지. 수정 전에는 여기서 통째로 실패했습니다.

## 7. 남은 한계

- **게스트 데이터는 여전히 이 브라우저에만 있습니다.** 로그인하기 전에 캐시를 지우면 사라집니다. 이 작업은 "로그인하면 건너간다"를 보장할 뿐, 로그인 전 보존은 불가능합니다
- **RPC 는 한 번에 1000개까지** 받습니다. 전체 문제가 377개라 실질 제약은 아닙니다
- `pyquests_sandbox_code`(샌드박스에 쓰던 코드)는 계정별로 스코프되지 않아 병합 대상이 아닙니다. 공유 PC 에서는 다음 사람에게 보일 수 있는데, **8번 작업(공유 PC 세션 처리)** 에서 다룰 항목입니다
